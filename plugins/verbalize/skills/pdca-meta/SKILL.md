# PDCAメタフレームワーク

## 概要

このスキルは2層のループ構造を持つ自律的な問題解決フレームワークである。

- **内側ループ**: 具体的な問いに対してPDCA（問の定義→工程構築→実行→評価）を回す
- **外側ループ**: 内側ループの評価結果を蓄積し、フレームワーク自体（パターン集）を改善する

入力は「言語化された問い＋評価基準」であり、言語化スキルの出力を想定している。
出力は「問の解決結果」と「フレームワークの改善記録」の両方である。

## ディレクトリ構成

スキル定義（配布物）と実行データ（ログ・パターン集）は物理的に分離する。

### スキル定義（`.claude/skills/pdca-meta/` 内 — 配布対象）

```
.claude/skills/pdca-meta/
└── SKILL.md              ← このファイル（不変の骨格）
```

### 実行データ（`{プロジェクトルート}/.pdca-data/pdca-meta/` 内 — 配布対象外）

```
.pdca-data/pdca-meta/
├── guardrails.md         ← 人間が定義する制約条件
├── references/
│   ├── patterns.jsonl    ← パターン集（外側ループで進化する）
│   └── eval_summary.json ← 評価の集計（通常はこれだけ読む）
└── logs/
    ├── eval_log.jsonl    ← 内側ループの評価記録（生ログ・振り返り用）
    └── meta_log.jsonl    ← 外側ループの改善記録（生ログ・振り返り用）
```

**ディレクトリ自動作成**: 実行データのディレクトリが存在しない場合は、最初の書き込み時に自動作成すること。

### コンテキスト消費を抑える設計原則

- **通常読み込み**: `patterns.jsonl` と `eval_summary.json` のみ読む
- **生ログ（eval_log.jsonl, meta_log.jsonl）は通常読まない**: 追記のみ行い、振り返り時に人間が明示的に指示した場合のみ読む
- **eval_summary.json**: 外側ループの判定に必要な集計値を保持する。生ログ全件読みの代替

### パス解決ルール

本SKILL.md内で `references/`、`logs/`、`guardrails.md` と記述されている箇所は、すべて `{プロジェクトルート}/.pdca-data/pdca-meta/` からの相対パスを意味する。スキル定義ディレクトリ（`.claude/skills/pdca-meta/`）内には実行データを配置しないこと。

## 入力仕様

言語化スキル（または人間）から以下の構造で入力を受け取る：

```json
{
  "question": "言語化された問い（何を解決したいか）",
  "context": "問いの背景や前提条件",
  "eval_criteria": [
    {
      "criterion": "評価基準の名前",
      "description": "何をもって成功とするか",
      "weight": 1.0
    }
  ],
  "constraints": "制約条件（任意）"
}
```

入力がこの形式でなくても、対話を通じてこの構造に整理するところから始めてよい。

## 内側ループ：具体的な問いに対するPDCA

### Step 1: パターンマッチング

問いを受け取ったら、まず `references/patterns.jsonl` を読み込み、既存パターンとの類似度を判定する。

**判定基準：**
- 問いの種類（技術的課題、組織課題、設計判断、学習課題 など）
- 問いの構造（因果関係の分析、選択肢の比較、未知の探索 など）
- 過去に似た問いで有効だったアプローチ

**判定結果に応じた分岐：**

| 状況 | アクション |
|------|-----------|
| 近いパターンがある | そのパターンをベースに Step 2 へ |
| 近いものがない | LLMの汎用推論力で仮の工程を構築し Step 2 へ（新規パターン候補としてマーク） |

パターン集はあくまで「過去の知恵による加速装置」であり、パターンがなくても止まらない。

### Step 2: 問の定義（Plan-1）

問いを解決可能な単位に分解する。以下の観点で構造化する：

1. **本質の特定**: この問いが本当に解こうとしていることは何か
2. **スコープの確定**: 何を含み、何を含まないか
3. **前提の明示**: 暗黙に仮定していることを洗い出す
4. **依存関係の整理**: 他の問いや外部要因との関係
5. **評価基準の確認**: 入力の eval_criteria を具体的な判定方法に落とし込む

出力形式：
```json
{
  "core_question": "本質的な問い（1文）",
  "sub_questions": ["分解された小さな問い"],
  "scope": { "in": ["含むもの"], "out": ["含まないもの"] },
  "assumptions": ["明示された前提"],
  "dependencies": ["依存関係"],
  "eval_methods": [
    {
      "criterion": "評価基準名",
      "method": "具体的な評価方法",
      "threshold": "合格ライン"
    }
  ]
}
```

### Step 3: 工程構築（Plan-2）

分解された問いに対して、解決のための工程を組み立てる：

1. **アプローチの選択**: パターンがあればそれをベースに、なければ推論で構築
2. **工程の分解**: 検証可能な単位のステップに分ける
3. **順序づけ**: 依存関係に基づいてステップを並べる
4. **各ステップの定義**: 入力・処理・出力・完了条件を明記する
5. **チェックポイントの設置**: 途中で方向修正できるポイントを入れる

各ステップの定義：
```json
{
  "step_id": 1,
  "name": "ステップ名",
  "input": "このステップへの入力",
  "action": "具体的にやること",
  "output": "期待される出力",
  "done_when": "完了条件",
  "checkpoint": true
}
```

工程全体をガードレール（`guardrails.md`）に照らしてチェックする。
ハードガードレールに抵触する工程は生成しない。
ソフトガードレールに抵触する工程には警告を付与する。

### Step 4: 実行（Do）

構築した工程に従って実行する。各ステップ完了時に以下を記録する：

- 実際の出力
- 予定と異なった点
- チェックポイントでの判断（続行 / 修正 / 中止）

実行中にガードレールへの抵触が検知された場合は、即座に停止して人間に判断を委ねる。

### Step 5: 評価（Check）

Step 2 で定義した eval_methods に基づいて評価する：

1. 各評価基準について、method に従い threshold と比較する
2. 全体スコアを weight に基づいて算出する
3. **ログ記録（必須）**: 以下の手順で記録すること。Step 6 に進む前に完了させること
   a. `.pdca-data/pdca-meta/logs/` ディレクトリが存在しなければ作成する
   b. `eval_log.jsonl` に評価結果を1行のJSONとして追記する
   c. `.pdca-data/pdca-meta/references/` ディレクトリが存在しなければ作成する
   d. `eval_summary.json` を更新する（集計値）

eval_log のレコード形式：
```json
{
  "timestamp": "ISO8601",
  "question_hash": "問いの識別子",
  "pattern_used": "使用したパターンID（または 'new'）",
  "eval_results": [
    {
      "criterion": "評価基準名",
      "score": 0.8,
      "detail": "評価の詳細"
    }
  ],
  "overall_score": 0.8,
  "notes": "特記事項"
}
```

### Step 6: 改善（Act）

評価結果に基づいて次のアクションを決定する：

| 評価結果 | アクション |
|---------|-----------|
| 十分に良い | 完了。外側ループへ結果を渡す |
| 部分的に不足 | 不足部分の工程を修正して Step 4 から再実行 |
| 根本的にズレている | Step 2 に戻って問の定義からやり直す |

内側ループの繰り返しは最大3回を目安とする。3回で収束しない場合は人間に状況を報告し判断を仰ぐ。

## 外側ループ：フレームワーク自体の改善

内側ループが完了するたびに、以下のプロセスでパターン集を更新する。

### トリガー

外側ループは以下のタイミングで起動する：
- 内側ループが完了したとき（毎回）
- 同種の問いが一定数（目安：3件以上）蓄積されたとき
- 人間が明示的にフレームワーク改善を要求したとき

### パターン進化の意思決定

`references/eval_summary.json` の集計データに基づき、以下の判定を行う
（生ログ `logs/eval_log.jsonl` は読まない）：

**1. パターンの新規登録**
- 条件: `pattern_used` が `"new"` で、overall_score が閾値（0.7）以上
- アクション: 使用した工程構築の方法をパターンとして `patterns.jsonl` に追加

**2. パターンの微調整**
- 条件: 既存パターンを使い、overall_score がまあまあ（0.5〜0.8）で、特定の工程に改善点がある
- アクション: パターン内の該当工程テンプレートを更新、変更理由を記録

**3. パターンの切り替え探索**
- 条件: 既存パターンを使い、overall_score が低い（0.5未満）
- アクション: 他のパターンでの再実行を検討。適合するものがなければ新規パターン候補として扱う

**4. パターンの廃止**
- 条件: あるパターンの直近の使用（5件以上）で平均 overall_score が継続的に低い
- アクション: パターンを非推奨としてマーク（即削除はしない）

### メタ評価

パターン更新の効果を `logs/meta_log.jsonl` に記録する（**必須** — パターン更新を行った場合は必ず記録すること）：

```json
{
  "timestamp": "ISO8601",
  "action": "add | update | explore | deprecate",
  "pattern_id": "対象パターンID",
  "reason": "変更理由",
  "before_avg_score": 0.6,
  "after_avg_score": null,
  "change_detail": "変更内容の要約"
}
```

`after_avg_score` は後続の内側ループで同種の問いが処理された後に埋まる。
これにより「この改善は実際に効果があったか」を追跡できる。

### 自律改善の制約

外側ループが自律的に行えるのは以下に限る：
- パターンの新規追加（ただし既存パターン数の2倍を超えない）
- パターンの微調整（変更量がパターン全体の30%以内）
- パターンの非推奨マーク

以下は人間の承認を必要とする：
- パターンの完全削除
- パターンの大幅な書き換え（30%超の変更）
- ガードレール自体の変更提案

## ガードレール

`guardrails.md` に人間が定義する制約条件を記述する。
このファイルはスキルの骨格の一部であり、外側ループからは変更できない。
変更できるのは人間だけである。

ガードレールは2種類ある：

### ハードガードレール（違反時は即停止）

工程構築時および実行時に常にチェックする。抵触した場合は処理を停止し、
人間にその旨を報告して判断を委ねる。

例：
- 本番環境への直接変更を含む工程を自動実行しない
- 個人情報や機密情報を含む出力をログに記録しない
- 設定されたコスト上限・時間上限を超える工程は人間承認を必要とする

### ソフトガードレール（違反時は警告＋評価への反映）

工程構築時にチェックし、抵触する場合は警告を付与する。
評価時に減点要素として扱う。

例：
- チームの合意を経ないプロセス変更は「提案」にとどめる
- 既存の運用ルールと矛盾する工程には代替案を併記する
- 外部への影響がある工程には影響範囲の明示を求める

詳細は `{プロジェクトルート}/.pdca-data/pdca-meta/guardrails.md` を参照すること。
初回利用時に `guardrails.md` が未作成の場合は、テンプレートを `.pdca-data/pdca-meta/guardrails.md` に生成し、
人間に記述を促す。

## eval_summary.json の形式

`references/eval_summary.json` は外側ループが生ログの代わりに読む集計ファイルである。
内側ループのStep 5完了時に、生ログへの追記と同時にこのファイルを更新する。

```json
{
  "patterns": {
    "<pattern_id>": {
      "use_count": 3,
      "avg_score": 0.78,
      "recent_scores": [0.8, 0.75, 0.8],
      "last_used": "ISO8601"
    }
  },
  "new_pattern_runs": [
    {
      "question_hash": "問いの識別子",
      "score": 0.83,
      "timestamp": "ISO8601",
      "registered_as": "pattern_id or null"
    }
  ],
  "total_runs": 5,
  "last_updated": "ISO8601"
}
```

- `recent_scores`: 直近5件のスコアを保持（FIFO。古いものから押し出す）
- `new_pattern_runs`: `pattern_used` が `"new"` だった実行の記録。パターン登録後は `registered_as` にIDが入る
- 外側ループはこのファイルだけで4つの判定（新規登録・微調整・切替探索・廃止）を実行できる

## パターン集の形式

`references/patterns.jsonl` の各行は以下の形式：

```json
{
  "pattern_id": "一意な識別子",
  "name": "パターン名",
  "question_type": "適用される問いの種類",
  "question_structure": "適用される問いの構造",
  "approach": "アプローチの概要",
  "decomposition_template": "問の分解テンプレート",
  "process_template": [
    {
      "step": 1,
      "action_template": "ステップのテンプレート",
      "notes": "適用時の注意点"
    }
  ],
  "success_rate": 0.0,
  "use_count": 0,
  "status": "active | deprecated",
  "created_at": "ISO8601",
  "updated_at": "ISO8601"
}
```

パターン集が空の場合でも内側ループは動作する。
LLMの汎用推論力でゼロから工程を構築し、その結果が良ければ最初のパターンとして登録される。
つまり、パターン集は使えば使うほど育つ仕組みである。

## 実行フロー全体図

```
入力（言語化された問い＋評価基準）
  │
  ├─ 内側ループ ──────────────────────────┐
  │  ① パターンマッチング                  │
  │  ② 問の定義（Plan-1）                 │
  │  ③ 工程構築（Plan-2）← ガードレール照合 │
  │  ④ 実行（Do）                         │
  │  ⑤ 評価（Check）→ .pdca-data に記録     │
  │  ⑥ 改善（Act）→ 不足なら②or④に戻る    │
  │  └─ 最大3回 ──────────────────────────┘
  │
  ├─ 外側ループ ──────────────────────────┐
  │  ⑦ eval_log を分析                    │
  │  ⑧ パターン進化の判定                  │
  │     - 新規登録 / 微調整 / 切替探索 / 廃止│
  │  ⑨ patterns.jsonl を更新               │
  │  ⑩ meta_log に改善記録を追記            │
  │  └─ ガードレール変更は人間承認 ─────────┘
  │
  └─ 出力（解決結果＋改善記録）
```

## 初回利用ガイド

このスキルを初めて使う場合：

1. `.pdca-data/pdca-meta/guardrails.md` にテンプレートを生成するので、自分の状況に合わせて編集してもらう
2. `references/patterns.jsonl` は空の状態で開始する（パターンは使いながら育つ）
3. 最初の数回は内側ループの結果を人間に確認してもらい、評価基準の妥当性を調整する
4. 外側ループによるパターン登録が始まったら、最初の数件は登録内容を人間が確認する
5. 安定してきたら自律度を上げていく

## ツール使用制約

ファイルへの書き込み・追記を行う際は、以下のルールに従うこと：

- **ファイルの新規作成**: Writeツールを使う
- **既存ファイルの編集**: Editツールを使う
- **JSONLファイルへの追記**: Bashツールで `echo '...' >> file` を使う（1行追記に限定）
- **禁止**: Bashツールで `cat` コマンドをファイル書き込み・追記に使わない（`cat << 'EOF'`、`cat >` 等すべて禁止）
- **禁止**: Bashツールで `sed`、`awk` をファイル編集に使わない

この制約はこのスキルの実行中だけでなく、このスキルから派生するすべてのファイル操作に適用される。

## 注意事項

- このSKILL.md自体は外側ループから変更しない（不変の骨格）
- 変更されるのは `.pdca-data/pdca-meta/` 配下のファイルのみ（スキル定義ディレクトリ内には実行データを置かない）
- `guardrails.md` を変更できるのは人間だけ
- 内側ループが3回で収束しない場合は必ず人間に報告する
- パターン集の自律更新には上限があり、大きな変更には人間の承認が必要
